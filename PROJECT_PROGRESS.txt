MAP FIX (19 Oct 2026) - "the map is too old / does not show the location"
--------------------------------------------------------------------------------
Symptom: the map was a blank pale square with a single river line, and fixes
were ~600 m off.
Two real causes:
  1. Tiles: Esri World Street Map is years out of date and BLANK at z15+ in
     rural India (checked by downloading the exact z15 tile - river only).
     Google's street raster is blank there too; OpenStreetMap has village names
     (Khargram, Murshidabad) but no buildings.
  2. Accuracy: the tracker asked Android for Accuracy.Balanced = Wi-Fi/cell
     positioning (+-100 m .. 1 km). That is why two phones in the same room
     reported positions 1.2 km apart.
Fixes:
  - tracking.js now asks for Accuracy.High (real GPS) for the background task
    and for "Send location now"; distanceInterval 50 -> 25 m. NOTE: the setting
    applies when tracking starts, so Stop tracking / Start is needed once.
  - The map defaults to SATELLITE (Esri World Imagery, keyless); the layers
    button switches to Streets (OpenStreetMap) or Terrain (Esri Topo). Verified
    by rendering the generated HTML in a browser: village, houses and fields are
    clearly visible at z16/z17.
  - Follow-up (same day, user reported grey "Map data not yet available"
    squares when zooming in): measured REAL tile coverage by downloading the
    tiles at the target coordinates — Esri imagery is sharp to z18 and returns
    the grey placeholder at z19; Esri Topo stops at z17; OpenStreetMap stops at
    z16 (solid white after). Each layer now sets maxNativeZoom (18/17/16), so
    Leaflet enlarges the deepest real tile instead of showing placeholders.
    The Esri place-names overlay was REMOVED: where it has no data it serves a
    faint semi-transparent "Map data not yet available" ghost that darkened the
    imagery. Default single-device zoom raised 16 -> 17.
  - Markers draw an accuracy circle; popups show "Accurate to about N m", the
    fix time and its age; a round button re-centres on the latest fix; scale bar.
  - pushLocation also rolls up lastAccuracy / lastLocationAt / lastLocationSource;
    the device screen shows (+-N m) and warns when the newest fix is >3 min old.
  - The Leaflet page is built once and markers are pushed with injectJavaScript,
    so a new fix no longer reloads the WebView (pan/zoom survive).
OSM / Carto / Google / Esri tiles were all reachable from this network; Esri
imagery + labels + topo are used because they are keyless and consistent.

PHASE 4b COMPLETE — BLE beacon + helper relay PROVEN ON HARDWARE (19 Oct 2026)
--------------------------------------------------------------------------------
Build 9b409181 (Kotlin compiled clean in EAS). Installed on both phones:
  Samsung A50 (Android 11, SDK 30)  +  OPPO CPH2729 (Android 16, SDK 36).
Proof chain observed on device:
  beacon advertises -> helper scans (unfiltered, JS-side UUID match) -> connect
  -> GATT read 568 base64 chars / 426 bytes -> JSON.parse OK -> SQLite queue
  -> relay uploaded -> owner harvest "checked 5, decrypted 5" -> 5 fixes in
  History at 01:19:16-20. The Samsung's own queue held only 1 packet, so the
  other 4 were relayed by the OPPO = genuine 2-phone BLE relay.
Bugs found + fixed while proving it (all JS-side, no rebuild needed):
  1. Beacon returned success before Android confirmed advertising -> now listens
     to AdvertiseCallback; UI shows "advertising OK" or the real error code.
  2. Helper scan restarted with a no-op callback after any failure -> silently
     deaf; now resumes with the same listener + 400 ms settle delay.
  3. Scan used Android's service-UUID ScanFilter -> returns nothing on some
     Samsung stacks; now unfiltered scan + JS UUID matching.
  4. encodeUTF8 was missing from the tweetnacl-util import in meshBle.native.js
     -> ReferenceError swallowed by a bare catch and misreported as "packet
     truncated". The packet had been arriving intact all along.
  5. ble-plx 3.5.1: discoverAllServicesAndCharacteristics() resolves to the
     Device, NOT a Service[] — services come from connected.services().
Measured facts worth keeping:
  sealed packet = 417 JSON bytes / ~556-568 base64 chars; default BLE payload
  is 20 bytes, but Android's stack follows long reads by itself (one read
  returned all 568 chars at MTU 512). Advertise payload = 21 of 31 bytes.
  Samsung rotates its BLE address, so the same phone appears as several MACs
  and some connects fail with "Operation was cancelled" — harmless, keep going.
New UI affordances: "Radio check (list nearby BLE)" + per-step scan trace in the
result alert + live beacon status line.

CROSS-USER 2-PHONE PROOF (19 Oct 2026, 02:04-02:11 IST) - both sides driven over Wi-Fi adb
--------------------------------------------------------------------------------
Setup: Samsung A50 (saikat@outlook.com, beacon/stolen)  <->  OPPO CPH2729
(saikat@rpconsultancy.net, helper - a DIFFERENT account, which is the real
scenario: a stranger's phone relays for you).
  02:04:58  Samsung seals a fresh packet (id WdHHxQyityduvc54cS8c-1792355698968)
            and starts advertising; status "Beacon: advertising".
  02:09:37-53 OPPO scans with its OWN beacon off, hears ONE beacon address
            (70:4D:E1:BA:16:CB), connects 5x, reads 568 b64 chars / 426 bytes
            each time: "[mesh] read ok" + "[mesh] relaying packet" -> 5 relay docs.
  02:09:58  OPPO harvest of its own account: "checked 0, decrypted 0" -> it
            cannot read what it relayed. Proof it is a true helper.
  02:10:x   Samsung harvest: "checked 5, decrypted 5" -> 4 fixes land in the
            device history at 02:10:26-31, coordinates 24.17762,87.89685 = the
            position the Samsung sealed at 02:04:58 (only its key could decrypt).
Also re-verified on the OPPO alone: Android 16 advertises + scans + reads
simultaneously; Radio check lists nearby BLE devices.
Robustness fixes made while running this (all JS-only, pushed):
  1. Beacon no longer fails without a GPS fix (the OPPO refused to start with
     "Current location is unavailable"): try a fix, fall back to the last known
     position, then advertise anyway with an empty position. Harvest counts
     these as "pings without a position" and never plots a null fix.
  2. POST_NOTIFICATIONS is now requested when tracking starts - on Android 13+
     the tracking notification and theft alerts were invisible without it.
  3. Relay docs are de-duplicated: one upload per packet per scan (was: every
     re-read of the same rotating-address beacon added another identical relay
     doc), and the harvest skips packet ids it already folded in.
Permissions granted on the OPPO (ColorOS blocks "pm grant", so via the app's own
dialogs): POST_NOTIFICATIONS, READ_PHONE_STATE.
