5. LESSONS (don't relearn these)
--------------------------------------------------------------------------------
- Install APKs over USB/adb. Files-app installs flake ("invalid package");
  EAS links expire in 15 min — download immediately. Uninstall old app first
  on versionCode ties. Play Protect flags dev builds (SMS/BT perms) — allow.
- New native modules need a NEW dev build; guard new imports with lazy
  require() or old binaries red-screen (RNCWebViewModule lesson).
- Hermes has no crypto.getRandomValues — use expo-crypto getRandomBytesAsync,
  normalize bridge Arrays to Uint8Array. tweetnacl-util: decodeUTF8(str)->bytes,
  encodeUTF8(bytes)->str (backwards from intuition — caused a real bug).
- OSM tiles 403 mobile UAs; CARTO needs API keys now; Esri tiles are free/keyless.
- ble-plx is CENTRAL-ONLY (its own README) — hence the custom advertiser.
- expo-sms = composer only (user taps send). Same-operator SIM swap invisible.
- Metro serves JS to dev builds: JS-only fixes need only app reload (--clear
  if stale). `.easignore` allows `.env` to EAS but blocks `*.apk`, adb-tools.

6. RADIO TEST (PROVEN 19 Oct 2026 — reproduce in 4 taps)
--------------------------------------------------------------------------------
- Both phones: Bluetooth ON, Location ON, power saving OFF, screens awake,
  2-3 m apart, same Wi-Fi as Metro.
- Stolen: Mesh > Start BLE beacon -> status must read "Beacon: advertising".
- Helper: Mesh > Radio check (should list nearby BLE devices) then Helper BLE
  scan -> "1 packet(s) read and relayed"; beacon side shows "packet served".
- Owner account: Harvest my relays -> "checked N, decrypted N" -> fixes appear
  in that device's History.
- If it fails: the alert now prints a per-step trace (found beacon -> connected
  -> mtu -> services -> characteristics -> read/parse) and quotes the decoded
  payload head. Beacon status shows the AdvertiseCallback failure code.
- Measured: sealed packet 417 JSON bytes (~568 base64 chars) vs 20-byte default
  BLE payload — Android's stack handles the long read itself. Same phone shows
  several MACs (BLE address rotation) and may throw "Operation was cancelled".
- Wireless logs without USB: Developer options > Wireless debugging > ON; then
  `adb mdns services` to get the `_adb-tls-pairing` port, `adb pair <ip:port>
  <code>` with the 6-digit code, then `adb connect <ip:connect-port>`.

7. DEV-BUILD / DEVICE TRAPS FOUND THE HARD WAY (19 Oct 2026 PM)
--------------------------------------------------------------------------------
- NEVER dynamic import() anything on an offline-critical path. In dev builds
  import() fetches the module from Metro at first use; with Wi-Fi off it fails
  after ~15 s with a network error (that is the "Secure random unavailable" when
  sealing the beacon). Use static require()/import — the module then lives in
  the main bundle and works with zero internet. Production bundles inline it
  anyway, so this bug class ONLY shows up in dev builds — test offline paths in
  dev mode deliberately.
- Samsung "location broken" for hours: check `settings get global
  airplane_mode_on` FIRST. Airplane on + no SIM + indoors = zero fixes, and
  Google Maps fails identically (so it is not the app).
- Indoors the fused provider re-emits the same ±500 m network fix every ~5 s;
  anything that pushes on every update must throttle (see tracking.js
  ROUGH_FIX_GAP_MS) or it floods Firestore history/quota.
- The device screen auto-refreshes stale fixes on open/foreground; keep the
  manual "Send location now" as the forced path.
- Relay ownership: helpers upload to the top-level `relays` collection with
  `ownerId` = the BROKEN phone's owner; only that owner can read/decrypt them.
  A "Harvest my relays" on the HELPER's account showing "checked 0" for a
  packet it just relayed is EXPECTED - harvest on the owner's account.
  Relays are SINGLE-USE: harvest deletes them after decrypting, so a second
  tap (or a screenshot taken later) always shows "checked 0" - that is
  success, not failure. Confirm the real outcome in the owner's device
  History: a relayed fix appears with source "mesh".
- React Native Firestore runs with an IN-MEMORY cache by default (no
  persistence). A write made while the app is offline resolves locally and is
  LOST if the process dies before it syncs. During hardware tests verify
  writes against the REST API (project owner token in the firebase-tools
  configstore), not only the app UI, which reads its own cache back.
- adb-over-Wi-Fi dies whenever the phone's Wi-Fi cycles (svc wifi disable in the
  offline test): toggle Wireless debugging OFF/ON afterwards, then
  `adb mdns services` -> `adb connect <connect-port>`; a pairing code is only
  needed if the _adb-tls-pairing service appears.
